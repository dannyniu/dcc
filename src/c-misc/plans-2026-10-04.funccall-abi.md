Function Calls and Their ABI.
====

This pertains to time table item 2 "scalar function parameters", and
item 3 "aggregate types". Both concerns processing of declarations.

Turns out the C language specify only very little about declarations -
this includes the semantic of qualifiers, meaning of tag prefixes, and
pointer/array/function forms of declarators. The rest - layout of members,
passing of argument parameters, are up to ABIs to define.

The AST traverser would encounter declarations and sub-declarations.
Ideally, each sub-declaration should be processed by an Omega instance
in such way that the result of its processing propagates upwards consistently,
similar to how L1 cache propagates to L2 and ultimately to main memory.

But the first problem to face, is that embedded `struct` behave differently
from those from root-level declarations/definitions.

Ignore this for a momemnt, the second problem is that the completeness of
the definition of a type must not interfere with uses of the type that are
agnostic to its completeness.

Most notably, working context structure types and virtual types for working
function with prototypes taking those structures would be declared together,
and would be completed one after another.

---

The answer to the first problem, is that there're syntactic indicators:
- embedded `struct` would be part of a `member-declaration-list` or
  a `struct-or-union-specifier`
- whereas a root-level one would not.

The answer to the second problem requires deferring. Only when a function
call is encountered would its declaration be looked up:
- if the declaration is already fully processed, this information is then
  used for argument placement.
- if the declaration violates certain constraints in the C standard, error
  is generated.
- if the declaration had not been processed, it's processed and reusable
  results (e.g. placement of non-variadic arguments) are cached.

Operational Consideration
====

- (2026-10-04: this is general, may need a rewrite some time later) Semantic Traversal _encounters_ a Declaration.
1. Semantic Traversal *Invokes* Omega Instance to *Process* the Specifiers
2. Semantic Traversal *Evaluates* the Declarators one-by-one, and recursively descending.

The generic part consist of:
- a Traverser, invoking the Omega instance for each specifier and declarator to form declarations.
- a Resolver, finding information pertaining to existing declarations and definition on behalf of the Omega instance.

The non-generic (i.e. ABI-specific part) consist of an Omega instance, which:
- operates on metadata attached to AST nodes while traversing.
- acting as information source for the resolver.
