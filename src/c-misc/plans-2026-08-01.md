(: Notation and Terminology Definitions :)
====

## Setup

- There exists the main memory where results and operands resides.
- There exists zero or more registers where computations are efficient,
- Any cache between registers and main memory are assumed transparent,
  and the abstract model work as if it doesn't exist.
- Some registers may need to be saved by the caller and/or the callee,
- Some registers may need to be preserved for the system.

## Premise

- An instruction may:
  - Load from main memory into register(s),
  - Store from register(s) to the main memory,
  - Compute,
  - Do any non-proper subset of above.
- An instruction may:
  - require its operand to be a register,
  - require its operand to be a specific register,
  - require its operand to be from main memory,
  - be inefficient compared to other instructions,
  - be more efficient compared to equivalent combinitions of other instructions.
  - be not available on certain machines.

## Cookies

For as long as AND ONLY as long as operands and operations are `[[unsequenced]]`
(TODO: may add other execution semantics, or rename this tag), their results are.
For such operations, cookies are defined for their results, as the hash of
the operation and their operands; further if their operands are commutative,
the hash shall be the same if the order of the operands are changed.
Operations with identical cookies that're `[[unsequenced]]` are to have their
tree nodes 'merged' while AST converts to DAG.

The cookies are distinct for the results of all other operations and
all other operands.

(: Black-Box Treatment of Blocks :)
====

Because of the inconsistency of the placement of variables in registers,
further because of the nesting of conditionally executed blocks with
possibility of arbitrary jumps into and out of the said blocks,
**It is so decided that** they're treated like opaque function calls
and in such way as if all registers are assumed volatile,
- variables are force-loaded on block boundaries and after labels,
- variables are force-stored on block boundaries and before jumps.

(: Conversion from AST into DAG :)
====

The 1st phase of compiling a given function involves converting AST to DAG
and coloring the nodes with the cookies mentioned above.

The "compiler's mental picture" 'executes' the AST by performing computation
over 'cookies'. All branches are taken; all loops are executed exactly once.

Before the AST is converted to DAG, each node has only 1 consumer -
from its parent node; after merging nodes with same cookie,
the merged node has its consumer count incremented for each new
parent node it acquires.

(: Stack Allocations Estimate :)
====

The 2nd phase determines the static and dynamic stack sizes.
- The statically-sized part of the stack holds local variables:
  - The declarations are hoisted (yeah, no support for VLAs) and their size
    are accumulated upfront.
  - Objects with different alignment requirements are accumulated separately.
  - Objects with stricter alignments are placed at lower addresses on the stack.
  - DAG nodes with consumer count greater than one are also counted here.
- The dynamically-sized part of the stack holds temporaries for register spills:
  - Computation of the values of expressions happen in registers, which at this
    stage is assumed to have an infinite supply of.
  - Space needed for aggregate arguments to function calls (including the
    hidden initial for the return values) are computed. Arguments are evaluated
    in the reverse order of their placement on the stack - that is, last-popped
    is the first-evaluated.

(: Register Allocation :)
====

The "compiler's mental picture" 'executes' the DAG again, issuing loads, stores,
and computation instructions. This time, it looks for input operands first from
registers by looking at their cookies - if there's no matching operand, it'll
issue an additional load.

Load destinations are chosen
1. from whichever register available, then
2. from a register currently holding a `volatile` value.
3. finally, look ahead on the DAG, eliminating one-by-one registers with cookie
   correspond to used operands - the remaining or the last-to-be-eliminated
   register is chosen.

For instructions taking specific register(s) as (either input or output,
hereafter not reiterated) operand(s):
- a 'phony' instruction that takes arbitrary register operand is emitted first,
- when the actual instruction sequence is emitted, the "compiler's mental picture"
  mark the used registers as invalidated, so that later use of the operand will
  result in the 'mental execution' issue additional loads.

(: Miscellaneous :)
====

Some operands may be `volatile`-qualified, and are always loaded just before use
and stored on assignment. Additionally black-box boundary of blocks
and `goto`s and labels, also guaratee memory access actions.

Pointer dereference also behave like accessing `volatile`-qualified objects,
unless the pointer is `restrict`-qualified.

When part of a register is used (e.g. low 32-bit part of a 64-bit register),
the whole register is considered used.

The caller-saved registers are colored as invalidated for function calls,
ensuring the consistency of the register file's view.

(Added 2026-08-11) As a matter of pragmaticality, the identifier resolusion
mechanism used here does not traverse beyond the function body - any external
declarations are handled with a separate symbols keeper. And then there's the
issue that these symbols will need to be reloaded if there are opaque function
calls between adjacent reads.
