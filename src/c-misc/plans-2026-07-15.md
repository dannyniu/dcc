Agenda 2. Least-Actively Used Strategy for Register Allocation.
====

## Setup
- There exists the main memory where results and operands resides.
- There exists zero or more registers where computations are efficient,
- Any cache between registers and main memory are assumed transparent,
  and the abstract model work as if it doesn't exist.
- Some registers may need to be saved by the caller and/or the callee,
- Some registers may need to be preserved for the system.

## Premise

- An instruction may:
  - Load from main memory into register(s),
  - Store from register(s) to the main memory,
  - Compute,
  - Do any non-proper subset of above.
- An instruction may:
  - require its operand to be a register,
  - require its operand to be a specific register,
  - require its operand to be from main memory,
  - be inefficient compared to other instructions,
  - be more efficient compared to equivalent combinitions of other instructions.
  - be not available on certain machines.

## Compute

For as long as operands and results fit in the set of registers, they do.
When not, registers are evicted to memory (which includes heap and stack,
which are thereafter not reiterated) on least-recently used basis.

For as long as AND ONLY as long as operands and operations are `[[unsequenced]]`
(TODO: may add other execution semantics, or rename this tag), their results are.
For such operations, cookies are defined for their results, as the hash of
the operation and their operands; further if their operands are commutative,
the hash shall be the same if the order of the operands are changed.
Operations with identical cookies that're `[[unsequenced]]` are to have their
tree nodes 'merged' while AST converts to DAG.

The cookies are distinct for the results of all other operations and
all other operands.

## Store

Each declared variable:
- on assignment, receive the cookie of their right-hand-side operand,
- on any case of forced store as mentioned in Agenda 3, becomes invalidated.

A register is immediately stored to RAM when:
- it's evicted by any of the forced cases as mentioned in Agenda 3,
- it needs to make way for an about-to-be-used value
  (see "Operation of the Compiler" below)
- the variable is `volatile`-qualified,

## Load

When reading from a variable:
- if it's `volatile`-qualified, it's loaded from RAM.
- if it's invalidated due to any case of forced store, it's loaded from RAM.
- if it's not loaded into any register, it's loaded from RAM.
- if its cookie doesn't match that of the register as rememberd
  by "compiler's mental picture", it's loaded from RAM.
- if all of the above checks are passed, it's directly read from register.

## Operation of the Compiler

The "compiler's mental picture" maintains a list of stores and loads as it
steps from the top to the bottom of the function body. For every load that
lacks an available destination register, it looks ahead (i.e. for codes
yet-to-execute) to find the last register to be accessed, or if there's
none, choose from the last ones available.

**2026-07-20**:

The 1st phase of compiling a given function involves converting AST to DAG
and coloring the nodes with the cookies mentioned above.

Before the AST is converted to DAG, each node has only 1 consumer -
from its parent node; after merging nodes with same cookie,
the merged node has its consumer count incremented for each new
parent node it acquires.

The 2nd phase determines that required stack size. This works by:
- traversing post-order,
- keeping a record of maximum stack size by:
  - incrementing stack size for each additional operand node that
    have a zero ''pre-increment'' usage count - this count is initially zero.
  - decrementing stack size for each result node by the difference between:
    - the sum of the sizes of all operands whose nodes have usage counts equal
      to their consumer count - i.e. is the last consume of the said node.
    - the size of the result of the operation.
- the above rules apply mostly to expressions.
  - stack size for declarations are accumulated separately.
  - the currently tracked stack size (for expressions)
    are reset on statement boundaries.
- objects with different alignment requirements are accumulated separately.
- objects with stricter alignments are placed at lower addresses on the stack.

Agenda 3. Black-Box Treatment of Blocks.
====

Because of the inconsistency of the placement of variables in registers,
further because of the nesting of conditionally executed blocks with
possibility of arbitrary jumps into and out of the said blocks,
**It is so decided that** they're treated like opaque function calls
and in such way as if all registers are assumed volatile,
- variables are loaded on block boundaries and after labels,
- variables are stored on block boundaries and before jumps.

So now brings to the question of difference between strategies for
register allocation for (whole) functions of different complexity.
